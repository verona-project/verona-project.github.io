Language

Values, types, and expressions

Names are case-sensitive. Comments begin with ;. String and character literals are ASCII-only; strings are immutable NUL-terminated byte pointers.

Nominal data

(type point (product (x i32) (y i32)))
(type option (sum (none) (some i32)))

(function unwrap ((value option)) i32
  (match value
    ((none) 0)
    ((some number) number)))

Core expressions

  • let, do, and return bind, sequence, and return values.
  • array-of and index create and access fixed arrays.
  • field reads a product field; match destructures sums.
  • &, deref, load, assign, cast, and pointer-offset express memory access explicitly.

Polymorphism and metaprogramming

Generics

Generic declarations dispatch to exact-type implementations.

Type parameters

for binds type parameters; calls specialize before LLVM lowering.

Protocols

Protocols describe operations and constrain polymorphic functions.

Macros

Compile-time macros transform S-expressions and may generate top-level definitions.

Modules, declarations, and reader features

  • type declares transparent aliases, opaque handles, products, and sums.
  • function, constant, and variable introduce program definitions.
  • external-function imports a C symbol; native-export exposes a compatible function to C.
  • import, export, and :as organize dotted modules and qualified names.

Prefix a form with #+name to include it when a reader feature is available, or #-name when it is not. Native compilation provides platform, architecture, pointer-width, endianness, and object-format features. Add project features with repeated --feature NAME options.

#+darwin
(external-function mach-task-self
  "mach_task_self" () u32)

Metaprogramming

Compile-time functions

Macro bodies evaluate ordinary S-expressions and return forms for the compiler to expand and compile. A macro returns one expression form inside executable code, or may return a top-level definition sequence at top level. Source locations are retained by the compiler and restored after expansion. The declarations in the explicit base module are imported macros, not built-in evaluator functions.

Reader forms

'FORM quotes an S-expression, `FORM quasiquotes a template, and ,FORM evaluates and inserts an S-expression inside that template. They are reader and evaluator forms, not function bindings.

(import base)

(base:macro generated-function (type)
  `(base:function ,(keyword-concat (keyword "generated-") ,type)
     () ,type 42))

Compiler surface

Surface forms and compiler definitions

Ordinary top-level declarations mechanically rewrite to compiler-recognized %… definitions. Application code should use the surface forms.

Surface formCompiler definitionPurpose
type%typeAlias, opaque, product, or sum type.
function%functionFunction declaration.
external-function%external-functionImported C symbol.
macro%macroSyntax transformation.
constant%constantImmutable global.
variable%variableMutable global.
generic%genericGeneric callable declaration.
protocol%protocolProtocol declaration.
implementation%implementationGeneric or protocol implementation.

Top-level module directives do not have %… equivalents: import, export, and native-export.

Reserved vocabulary

Verona has contextual keywords rather than one globally prohibited identifier list. Treat the following spellings as reserved in their listed positions.

Reader literals

unit, true, false, numbers, strings, and #\… characters.

Reader syntax

(, ), ", ;, #+feature, #-feature.

Type language

pointer, array, function, product, sum, for.

Modules

import, export, native-export, :as, ., :.

Expressions

do, let, match, return, array-of, index, field, load, assign, store, cast, pointer-offset, &, address-of, deref, dereference.

Patterns and internals

_ is a wildcard pattern. The compiler owns the %… definition and primitive namespaces.

Predeclared types are bool, char, void, i8…i64, u8…u64, isize, usize, f32, f64, and exit-code. Predeclared generic operators are +, -, *, /, ==, !=, <, <=, >, and >=.

Tooling

Command line and declarative builds

Commands

verona --version
verona compile SOURCE [options]
verona build TARGET OUTPUT-DIRECTORY [--feature NAME]...

compile builds one root source file. build finds verona.build in the current directory and writes the selected target beneath the output directory.

Build file

(executable app
  (root app.main)
  (module-path "src")
  (optimize 2)
  (library "sqlite3"))

Build files are declarative data: Verona forms inside them are never expanded or evaluated.

Executable arguments

An executable can receive the platform command line with a C-compatible entry declaration. argc includes the executable name; argv points to its NUL-terminated byte strings.

(function main ((argc i32) (argv (pointer (pointer u8)))) exit-code
  (let ((first-argument (pointer u8)
                        (load (deref (pointer-offset argv 1)))))
    ; parse first-argument when argc is at least 2
    0))

pointer-offset advances a pointer by an integer number of pointee elements. It requires a pointer to a complete type; as with C pointer arithmetic, the program owns bounds and lifetime safety. Existing zero-argument main declarations remain supported for compatibility.

verona.build clauses

A build file contains one or more executable, static-library, or shared-library declarations. Every target requires exactly one (root module.name) clause.

ClauseDescription
(root module.name)Required root module.
(module-path "PATH")Add a module search path; repeatable. Defaults to the build file directory.
(target native)Use the native target; the default.
(target "TRIPLE")Use an explicit LLVM target triple.
(optimize 0)…(optimize 3)Set optimization; default is 0.
(version "VERSION")Declare a release version for the target.
(features NAME...)Set target reader features; may appear once.
(library "NAME")Link a native library; repeatable.
(library-path "PATH")Add a native library-search path; repeatable.
(framework "NAME")Link a Darwin framework; repeatable and Darwin-only.
Relative module and library paths are resolved from the directory containing verona.build. Reader features are layered as target-provided features, command-line --feature values, then the target’s (features ...) clause.

Verona package environment

Verona packages use two required, independent absolute environment variables: VERONA_SOURCE_DIR identifies the canonical package-source root, and VERONA_LIBRARY_DIR identifies the canonical installed-artifact root. Future Verona install and package-discovery commands use the same pair, so a user-local environment can remain isolated from a shared installation.

export VERONA_SOURCE_DIR="$HOME/.local/src/verona"
export VERONA_LIBRARY_DIR="$HOME/.local/lib/verona"

These variables are only for Verona packages. Native C libraries remain build-specific: pass their locations with -L/--library-path, names with -l/--library, or use pkg-config.

Current limits

Designed boundaries

  • Unicode strings and characters are not supported yet.
  • Recursive inline type layouts are rejected.
  • Opaque values cannot be materialized or dereferenced.
  • Nested sum constructor patterns are not supported.
  • Numeric conversions are always explicit.
